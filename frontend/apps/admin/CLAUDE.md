# CLAUDE.md — frontend.admin

Guidance for working inside `frontend/apps/admin`: Next.js 15 (App Router) + Refine 5 + MUI 6, run with the `refine` CLI, talking to api-gateway through the `@frontend/proto` / `@packages/proto` gRPC clients. Refine's data providers live in `features/grpc/providers`, its auth provider in `features/auth/providers`; `src/common` holds the shared UI, hooks and helpers.

## What it is

The admin panel. Refine resources under `src/app/`: `auth/{users,temp-codes}` and `storage/{files,images,videos,storage-objects}`, each with list / show / edit / create (+ `create-many`) pages, plus auth pages (login, register, forgot-password), and a folder browser at `storage/storage-objects/[id]/content`.

## Data access (the core path)

1. Refine's `grpcDataProvider` (`'use client'`, `features/grpc/providers`) delegates every CRUD call to **Next server actions** (`'use server'`, `features/grpc/actions/grpc.data.actions.ts`).
2. Those actions resolve a repository by resource via `grpcDataService.getRepository(resource)` (`features/grpc/services/grpc.data.service.ts`) and call `getById`/`getList`/`createOne`/… on the **`Grpc*AdminRepository`** variant from `@frontend/proto` — the admin panel talks to the api-gateway `Admin` audience.
3. **gRPC runs on the Next server, not in the browser** — `@grpc/grpc-js` is a Node client. Browser → server action → gRPC → api-gateway (`BACKEND_GRPC_URL`). `authService.getAuthMetadata()` injects the JWT into gRPC metadata on every call.
4. **A server action never throws; it returns an `ActionResult`** (`features/grpc/types`). Wrap its body in `runAction`. The caller unwraps with `unwrapActionResult`, which throws an `Error` carrying `statusCode`, the `HttpError` Refine reads, and `retryAfterMs` for a call the gateway's rate limit refused. **A query waits that out before its next try**: the `QueryClient` Refine builds takes `getQueryRetryDelay` (`common/helpers/query-retry.ts`) as its default `retryDelay` — `retryAfterMs`, else React Query's own backoff — through `queryClientConfig` (`common/providers/query-client.config.ts`, a `'use client'` module: the root layout is a server component, and a function it passed to `<Refine>` itself would not reach the browser). A query that sets its own `retry` uses `retryUpTo(n)`, which retries a 429 and a server failure but no other 4xx. A 4xx keeps the backend's message. A 5xx or an error without a gRPC status gets a fixed message, and the original is logged on the Next server (`GrpcErrorMapper`, `features/grpc/mappers`; `reportError` does the mapping and the logging). An `app/api` route handler answers a caught error with `errorResponse(error)`, the same mapping as `{ message }` with its status — never `getErrorMessage`, which returns grpc-js `details` verbatim and is for client code. `run-action.ts`, `report-error.ts` and `error-response.ts` load grpc-js, so they are imported by path, and only from server modules. `features/grpc/helpers` has no barrel on purpose.

   > **Why failures travel as values:** [docs/adr/0020-server-action-failures-as-values.md](../../../docs/adr/0020-server-action-failures-as-values.md)

`features/grpc/repositories/index.ts` is the **single source** of `Admin` repository singletons (user, temp-code, file, image, storage-object, video). They are consumed by:

- `features/grpc/services/grpc.data.service.ts` — `GrpcDataService` builds the resource→repository map behind the CRUD data provider from these singletons (no longer instantiates its own).
- the binary-media **route handlers** (`app/api/*`) and the storage create/folder **server actions** (`features/storage/actions/*`), which import the storage repos directly.

The **auth** flow (`features/auth/services/auth.service.ts`) is separate and deliberately uses the `Web`/`Public` audiences (`GrpcUserWebRepository`, `GrpcAuthPublicRepository`): login / refresh / current-user are web-audience calls, not admin CRUD. `getAuthMetadata()` is the single source of gRPC metadata for every authenticated call, upload confirmations included. Login and refresh carry `getClientMetadata()` instead — the browser's address as `x-client-ip`, which the gateway rate-limits them by (see `backend/apps/api-gateway/CLAUDE.md`). The address comes from the one header `CLIENT_IP_HEADER` names (`getHeadersIp`, `common/helpers`), the one the proxy in front overwrites — never `x-forwarded-for` as sent, whose left end the client writes ([ADR-0035](../../../docs/adr/0035-client-address-from-one-trusted-header.md)). **A signed-out session is thrown as a gRPC status, never a plain `Error`** (which `runAction` reports as a 500): a missing or refused refresh token is `UNAUTHENTICATED` (`features/auth/helpers/session-error.ts`, imported by path), a non-admin `PERMISSION_DENIED`. The auth provider reads a 401 / 403 as logged out — `getIdentity` answers `null`, `onError` (reading `statusCode`) logs out. **An expired session is refreshed in `src/middleware.ts`** (Node runtime, for grpc-js), not in the page: a server component cannot write cookies, so a layout's own refresh reached the gateway, threw on the cookie write, and sent a valid refresh token to `/login`. The middleware puts the new cookies on the request (for this render) and the response, and deletes all four when the token is refused; `AuthService`'s own refresh is only the fallback for a server action. **One gateway refresh per refresh token:** a page's parallel requests all arrive without an access token, so `refreshSession` runs them through `SingleFlight` (`features/auth/helpers`) — concurrent callers share one call, and its success is reused for 30 s, for the requests the browser sent with the old cookie before the new one reached it. Only the flights' `Map` lives on `globalThis` (the middleware and the app are separate bundles), never the `SingleFlight` itself: an object that survives a dev reload keeps running the code it was built with. Logout forgets the flight by key **and** by the token it handed out — it is keyed by the old token, and the cookie holds the new one. **This is load-bearing, not an optimisation:** refresh tokens rotate, and auth ends a session whose token is spent twice, so the admin must run as **one process** — a second would refresh the same token on its own and log the user out ([ADR-0029](../../../docs/adr/0029-refresh-token-rotation.md)). **Logout revokes the session** (`AuthService.logout` calls the gateway's public `logout` with the refresh token, then clears the cookies): best effort — a failed call is logged and the cookies go anyway ([ADR-0028](../../../docs/adr/0028-refresh-sessions-in-postgres.md)). **It is a form post, not a server action:** `authProvider.logout` submits to `POST /api/auth/logout` (`LOGOUT_PATH`, `features/auth/helpers/logout-path.ts`), whose `303` loads `/login` as a new document — a sign-out `onError` asks for included. Do not turn it back into a soft navigation: the page left behind stays mounted and the query cache survives, so whatever a finished session's queries ask or hold — a 401 cached after the sign-out, the other user's rows — is read by the next sign-in, and a cached 401 makes the auth provider sign it out. The handler refuses a cross-site post, and the middleware lets the path through without refreshing ([ADR-0036](../../../docs/adr/0036-a-session-ends-with-a-document-load.md)).

## Binary media (separate path)

Upload, download, open, and player do **not** go through the data provider. Download/open/player use Next **route handlers** under `src/app/api/{files,videos}/[id]/...`, reached by browser navigation alone — `<a download>` (`DownloadButton`), `<a href>`, the preview `<Image>` — so no script reads their error body: a new tab shows the raw JSON, a download or an image just fails. **An embedded player is not one of them:** `BunnyPlayer` (`features/video/components`) loads the signed embed URL itself, fetched by the `getVideoPlayerUrls` server action and cached per video. The requests of one moment — a gallery page's videos, prefetched together — go in one gateway call (`createBatchLoader`, `common/helpers`), and a player keeps the URL it loaded first: a new one would reload the iframe and start the video over. Through the `player` route's redirect the iframe would end on another origin than its `src`, where its `allow` no longer applies — so no autoplay — and Player.js, the Bunny embed's control protocol, would post to the wrong origin. The `player` route is for a new tab only. The two download handlers proxy the signed CDN URL through `features/storage/helpers/download-proxy.ts` (imported by path): **never pass `request.headers` to that `fetch`** — it carries the admin's session cookies to a third party. `toUpstreamHeaders` forwards an allow-list (`Range`, `If-Range`, and `Referer` cut to its origin — the Stream pull zone rejects a request without an allowed referrer) with `Accept-Encoding: identity`, and `toDownloadResponseInit` returns the CDN's status (206 for a range) with `Content-Range` / `Accept-Ranges` / `ETag` / `Last-Modified`, so a browser can resume. **`next/image` runs unoptimized** (`images.unoptimized` in `next.config.mjs`): nothing resizes an image — the storage pull zone has no Optimizer — so an `<Image>` takes its `src` as given, with no `loader`, and the `open` handler redirects to the signed URL untouched ([ADR-0026](../../../docs/adr/0026-folder-listing-carries-signed-previews.md)). See `features/storage` (`use-single/multiple-file-upload`, uploader, per-type action providers) and `features/video`/`image`.

**No upload has a route handler — bytes go from the browser straight to Bunny.** `createOne`/`createMany` return the entity together with credentials, and both upload hooks take a required `uploadFileAction` (`features/storage/types`, the same `Action`-suffix trick as `createManyAction`, for Next's 71007 check) that spends them. Video: `uploadViaTus` (`features/video/helpers`) over Bunny Stream TUS. Files and images: `uploadViaPresignedUrl` (`features/storage/helpers`) PUTs to the pre-signed Bunny Storage URL (`putToPresignedUrl`), then calls the `completeFileUpload` server action — the folder browser's upload queue confirms many at once through `completeFileUploads` instead — and an image completes by its **`fileId`**, not its own id ([ADR-0015](../../../docs/adr/0015-file-uploads-presigned-s3-put.md)). `useMultipleFileUpload` keeps failed items with their created entity, so a retry creates only what has no row yet — or whose `upload.expires` is about to pass. That split and the merge of created entities back into the map are pure functions in `features/storage/helpers/upload-batch.ts`, unit-tested — change the retry rules there, not in the hook. A new selection replaces the old one, and the rows of dropped items (re-selected or removed from the failed list) are deleted through the generic `deleteOne` action, best effort. `VideoActionProvider`/`FileActionProvider`/`ImageActionProvider` flatten the `{ entity, upload }` pair so the hooks still see a flat record; the create pages strip `upload` before handing the record to Refine. **`uploadViaTus` disables tus's fingerprint URL storage on purpose** (`storeFingerprintForResuming: false`, no `findPreviousUploads`): that storage is keyed by the file, not by the `videoId`, so re-uploading the same file resumed the *previous* video's finished upload and left the new row `PENDING` with the UI claiming success. See [ADR-0014](../../../docs/adr/0014-video-uploads-bypass-the-backend.md).

The `file`/`image`/`video` resources are registered in `app/layout.tsx` with `dataProviderName: 'upload'` → a second data provider `grpcUploadDataProvider` (`features/grpc/providers`) whose `create`/`createMany` just echo their variables. Refine's built-in create step is intentionally a no-op for these: the entity row is created and its bytes uploaded by the create pages themselves (create/`create-many`) via the storage server actions + the direct upload helpers.

## Folder browser

`storage/storage-objects/[id]/content` shows one folder of a user's tree: Google Drive's grid and list, and Finder's gallery (`features/storage/components/folder-browser`). It is reached from a user's row (`UserStorageButton` looks up the root folder on click), from a folder's row or show page, and folder to folder from itself.

- **Not a Refine data-provider call.** A folder listing is not a CRUD list, so `useFolderContent` (`features/storage/hooks`) runs its own server action (`getFolderContent`) under `@tanstack/react-query` directly — the same client Refine sets up, pinned to Refine's version so both share one `QueryClient`. The admin `getFolderContent` needs the folder's owner too: a deep link reads the folder first, and every listing remembers the owner of each folder it names, so a step inside a tree is one gateway call.
- **The view's state lives in the URL** — `view`, `sortBy`, `sortOrder`, `page`, `pageSize`, the filters `search` / `types`, and `focus` (the item the keyboard is on: the gallery's selection, or in a grid or list the folder marked on the way up or the item last clicked — never the selection), parsed and patched by the pure `folder-content-params.ts`; a new sort, page size or filter goes back to page 1. A subfolder link keeps the layout and sort and drops the filters: `search` matches this folder's own items only. `setParams` writes through the native history API, which Next syncs with `useSearchParams` — the server renders nothing from these parameters, and a router navigation would fetch the page from it on every arrow key.
- **View and sort are remembered** in the `storage-folder-preferences` cookie (`folder-preferences.ts`), with whether the gallery shows its details. The page is a server component only to read it, so the first render already has them — no flash of the defaults, no listing fetched in the wrong order. The URL wins over the cookie, the cookie over the defaults; a value equal to the viewer's preference stays out of the URL, and only an explicit change (toolbar, list header, info toggle) saves one.
- **A click selects, as in Drive — in the grid and the list.** ⌘/Ctrl-click adds or takes an item, Shift-click selects the range from the anchor, a checkbox (under the pointer, and on every item once one is selected; select-all in the list's header) toggles one, and a drag on the empty space draws a selection box (`useMarqueeSelection`; ⌘/Shift add to what is selected, a click on nothing clears it). Held near the top or the bottom of the screen, the box scrolls the page and grows with it (`getAutoScrollStep`). It works in the container's own coordinates, and it ignores a press that reaches the container through a React portal — an item's open menu or its backdrop — which it would otherwise capture, keeping the menu from closing. The rules are the pure `folder-selection.ts` and `marquee.ts`; `useFolderSelection` holds the selection in memory and only the item the keyboard is on reaches the URL (`focus`). **A selection lasts across the folder's pages, sorts and both Drive views**, so it can be gathered page by page: ⌘A adds the page, the list's header checkbox takes the page back out, and an item on another page is remembered as it was when selected. A new folder or filter starts a new one, and so does the gallery, which keeps its own single selection; leaving the gallery drops its `focus`, so the grid and the list start with nothing selected. **A selection holds at most 100 items** (`MAX_SELECTION`, the gateway's cap on a batch call): whatever would grow it past that — a range, ⌘A, the marquee — keeps what was selected and takes new items in order until it is full, and says so (`capSelection`, applied in `useFolderSelection`'s one `update`).
- **A double click or Enter opens**, in every view: a folder in place, anything else in the full-screen viewer (below), as in Drive. The item itself — in a new tab through the `open` / `player` route handlers (`getFolderItemTarget`) — is the viewer's and the gallery bar's Open button, and the "⋮"'s Open in new tab. **Before its upload is READY an item opens nowhere**: the target is `unavailable`, Open is disabled, and the stage shows the upload's status with what it means (`getFolderItemUnavailableReason`) — the browser never sends the viewer to a show page for it. **A FAILED one is offered "Upload again" and "Delete" there** — and so is one still PENDING whose upload died in this tab (`useUploadOf`: the queue holds it as failed). "Upload again" is in the item's "⋮" and its right-click menu too, where Open would stand, for one item only (`StorageItemActionsMenu`, by the same `getItemUploadState`). `useUploadAgain` deletes the failed item — its name is free at once — and queues a file in its place: the one this tab's queue still holds for that file row (`findFailedUpload`), with no picker, else a picked one, and nothing is deleted until a file the queue takes is there. A failed row cannot take the bytes itself, since only a create call hands out upload credentials. The queue's own failed entry for the row goes too (`dismissFailedOf`): its retry would upload into a deleted record. **The deleted item stays on the page until the new one is listed**, so the viewer stands still and never visits a neighbour: every view takes its items from `useUploadAgain` (`holdReplacedItem` puts the item back where it stood, in the listing it stood in — folder, page, order, filters — and the viewer's total counts it), and `getReplaceStep` (`upload-replace.ts`, pure) swaps it for the new item, found by its file row (`getUploadFileId`), moving the view there when it still stands on the held one. An upload dismissed or cancelled, or failed before its record was made, lets the item go, and so do five seconds without the new item once the upload rests — it landed on another page. **Nothing acts on the held item — it is deleted already**: its "⋮" rests (`isReplacedBy`, read off the queue by the menu itself), `FolderBrowser` leaves it out of every rename, move, delete and visibility change, whatever asked — a key, the selection's bar, a drag — and once let go it leaves the selection. **An item this tab is uploading shows the progress in place of its row's status** (`useUploadOf` → `getUploadProgress`) — on its stage and on its tile (`StorageItemUploadBadge`, over the thumbnail, which shows the row's status otherwise), and in a row of the list in place of its icon, which has no room for a badge beside a name (`StorageItemRowIcon`: a ring for the progress, a mark for a failed upload, a clock for one still awaited, the words as its title). Which of the three an item is at is one pure rule, `getItemUploadState` (`upload-queue.ts`), that the stage and the row both read — change it there: its own upload, or the one taking its place, which the queue's entry names (`replaces`). `useUploadOf` redraws an item for its own upload alone, since the queue changes with every percent of every file. The stage has "Cancel upload" while the upload is on its way, and on a tile the badge gives way to it under the pointer, as a row of the upload box does (`useCancelItemUpload`): the upload is cancelled and the item leaves the cached listings at once, as a deleted one does. The tile's cancel swallows the rest of a double click — the card that moves under the pointer would be selected and opened by it. An abandoned PENDING upload turns FAILED by itself once its upload window has closed (the storage cleanup cron). The kind behind an icon is `getStorageItemKind` — storage type, then MIME type, then extension. Going up — ⌘↑, Backspace, a breadcrumb, Back — marks the folder just left, on the page it was on (`getChildOnPath`, a per-folder last page), as Finder does. Marked is not selected (`focusOnly`): the folder is outlined and has the keyboard — Enter opens it, the arrows start from it — but a checkbox, a ⌘-click or Delete never takes it along unseen.
- **Move, delete and visibility act on the selection**, from the bar that lies over the toolbar while something is selected (the toolbar keeps its place, so nothing below jumps), or from an item's "⋮", which acts on the whole selection when the item is part of it and otherwise selects the item alone. Each is one gateway call, all or none (`deleteStorageObjects` / `moveStorageObjects` / `setStorageObjectsPublic`) — the selection's cap makes sure it fits; one call per item would run into the gateway's per-user rate limit. **The "⋮" has no Edit and no Details, and neither has the folder's header**: the browser links to no show page at all. It renames in place (`RenameStorageItemDialog`, one item only, as in Drive — a file's name comes selected without its extension, a taken name is the backend's 409 shown on the field) and carries a Public switch; the bar has Make public / Make private. A folder's visibility reaches its whole subtree, and in a public folder nothing can be made private — the service refuses it, and the switch and Make private are disabled there. `patchFolderListings` writes a rename or a visibility change into every cached listing before the refetch. Its notifications go through `useReplacingNotification` (`common/hooks`): notistack renders every snackbar it holds under its `key`, so a second one under a key still on screen — two quick visibility changes — rendered two children with one React key; there a `key` names a group whose last notification closes as the next one opens under a fresh key. A move goes through "Move to…" (`MoveStorageItemsDialog`, on the folder picker below: it opens on the current folder, which is no target, and the moved folders cannot be entered), or by dragging onto a folder of the page or a breadcrumb above (`useFolderItemBehavior`: native drag and drop under the private `application/x-storage-objects` type, carrying the selection or the dragged item alone). A name taken in the target comes back suffixed, never refused, and the notification lists the renamed items (`getRenamedItems`). A delete asks first (`DeleteStorageItemDialog`, one item or several): the service marks the items — each folder with its whole subtree — deleted, with no restore. `useDeleteStorageObjects` and `useMoveStorageObjects` drop the items from every cached listing at once (`dropFromFolderListings`), then invalidate them; the gallery deletes or moves its one item the same way — from its bar's "⋮", the viewer's, or a right click in its strip — and selects its neighbour.
- **"New" has three entries, and none opens a form:** Folder, File upload, Folder upload (`FolderNewMenu`). Folder asks for a name in `CreateFolderDialog` — Drive's, "Untitled folder" selected to type over — and makes it in the folder shown through `useCreateFolder`. The folder takes its visibility from the one it is made in: the action sends `isPublic: false` and the service turns it public inside a public folder. A taken name is the backend's 409 shown on the field.
- **A right click opens Drive's menus by the pointer:** an item's own "⋮" in the grid, the list and the gallery's strip (`StorageItemActionsMenu` — the menu `StorageItemMenu`'s button opens, here hung from a point), and "New" on the empty space around the items of the grid and the list, the list's header row included (`FolderNewMenu`'s one menu, at its `position`; its pickers stay mounted, since a picker answers after the menu has shut). `FolderBrowser` holds one `contextMenu` for both, so only one is open. A right-clicked item becomes the selection unless it is part of it, as its "⋮" makes it (`ensureSelected`) — in the strip, the gallery's one selected item — and one on the empty space clears it, as a click there does; the item held on its page while it is uploaded again has no menu. Both handlers are `openOwnMenu` (`context-menu.ts`), which hands the click over with its point — the focused item's corner when the keyboard's menu key made it — and leaves alone a click that was made in a menu the element has open: a portal's events reach its owner through React's tree, not the DOM's. **A right click beside an open menu moves it, as in Drive** (`passRightClickOn`, the `onContextMenu` of every menu here — the "⋮"'s and New's own button's too): it lands on the menu's backdrop, shuts the menu, and is made again on what lies under the backdrop, which opens its own menu there or, having none, opens nothing; one on the menu itself does nothing. The item's menu is keyed by its point, so it opens anew there and its first entry takes the focus. Both handlers are covered by `context-menu.spec.ts`, on node like every suite here: its elements are fakes with no more than the handlers ask of one, since jsdom has no `elementsFromPoint` to offer either. **The gallery's stage keeps the browser's own menu** — an image's, a player's — and so do the header, the breadcrumbs and the search field; only an empty folder has "New" under the pointer in that view.
- **Files and folders dropped from the desktop upload in place, as in Drive** — onto the folder anywhere, or onto a subfolder or a breadcrumb, which outlines and names the target (`useFileDrop`, and `useFolderItemBehavior` for a folder, which tells a desktop drag — `Files` — from its own private type); "New → File upload" / "Folder upload" (`webkitdirectory`) pick them instead. **A folder comes with its whole tree**: `readDroppedTree` (`upload-tree.ts`) walks a drop through the entries API — the items are taken inside the drop event, which empties them, and only the walk runs after it — and `readDirectoryInput` reads a picked one from `webkitRelativePath`; both leave out `.DS_Store`, `Thumbs.db` and `desktop.ini`. Every folder of the tree, empty ones included, is made by one `createFolders` call before any file is queued (at most `MAX_TREE_FOLDERS`, 500, the gateway's cap), and shows in the listing at once; a top-level name taken in the target comes back suffixed (` (n)`), like a move's. `sortUploads` (`upload-rules.ts`) makes an image or a video its form takes one, keeps anything else a plain file, and leaves out an empty file and one over its kind's limit, saying which. `UPLOAD_RULES` there are the one copy of those limits and types, which the create forms read as well. The files join `storageUploadQueue` (`use-storage-uploads.ts`), each into its own folder: a store outside React, so an upload outlives the page it started on. **Every step that calls the gateway takes many files** (`pickUploadWork` in `upload-queue.ts`), since its rate limit counts calls, not files: records are made with one `createMany` per kind and folder (ten files or images, a video only on its turn, as its credentials are ticking); a file or an image, once its bytes are PUT (`putToPresignedUrl`), waits as `uploaded` and is confirmed with others by one `completeFileUploads` call — twenty at most, sent when the batch is full, the oldest has waited a second, or nothing else is on its way — whose answer is per file. A video needs no confirmation (its webhook does it). A call refused by the rate limit (429) puts its items back and pauses the queue rather than failing them — until the gateway's window resets (`retryAfterMs`, from its `retry-after` trailer), or 30 s when it did not say (`getRateLimitPause`). Three transfers run at a time. A failed item keeps its record for a retry while the credentials last (`hasUsableCredentials`), and a dismissed one has its record deleted, best effort. **An upload still on its way can be cancelled** (`cancel`; `isUploadActive`): it leaves the queue as if never dropped — its transfer is aborted (an `AbortSignal` into `putToPresignedUrl` / `uploadViaTus`) and its record deleted, which takes the folder item and the provider's bytes with it (the storage service cascades); a record still being made is deleted as its create call answers. The item leaves the queue before the transfer is aborted, and by key: an aborted PUT reports its last progress as it dies, and that write would otherwise bring the item back. No new RPC — a cancel is the delete the dismiss already made. `StorageUploadPanel`, mounted once in `app/layout.tsx`, is Drive's box in the corner: progress, which gives way to a cancel under the pointer or the keyboard's focus, as Drive's does (on a screen that does not hover the two stand side by side; a folder's row cancels its files still on their way; a double click's second click is ignored, since the next row has moved under the pointer), retry — an uploaded folder as one row for all its files, by the top of its tree each queued file carries (`group`; `groupUploads` / `getUploadRowStatus` in `upload-queue.ts`), retried for its failed files and dismissed whole, and unfolded on a click to its files, the failed ones first with their errors — and a refresh of the folder listings and media lists as items finish or fail (a failed upload's record sits in its folder, where the stage offers to send it again) and as the queue's records change (`getRecordChanges`): made — a record is a folder item from then on, so a file shows in its folder, with its progress and its cancel, while its bytes are still on their way, and an item uploaded again is swapped in as soon as it is listed — or deleted behind a cancelled or dismissed upload, counted once the delete call is back. A refresh owed stays owed through a dismiss, which reruns the effect that times it; it asks before the page is left mid-upload. **Its close is Drive's, and always empties it**: it forgets the uploads that have ended — a failed one with its record — and with some still on their way it cancels those first, once `CancelUploadsDialog` has confirmed it, an `alertdialog` with "Keep uploading" in focus, since one click would otherwise throw away a long transfer. **The full-screen viewer folds the box to its header** (`useFoldUploadPanel` in `GalleryViewer`, read by the box through `useIsUploadPanelFolded` — a counter outside React, like the queue): open, it lies over a corner of the stage, and on a narrow window over the stage's own buttons. Opened by hand there it stays open, and it is back as it was once the viewer is left. A file dropped beside the folder is swallowed, not opened in the tab.
- **Thumbnails come from the listing's `previewUrl` only**, never an original ([ADR-0027](../../../docs/adr/0027-image-preview-made-on-upload.md)); one that fails to load refetches the listing, at most every 30 s, since its signature has likely expired ([ADR-0026](../../../docs/adr/0026-folder-listing-carries-signed-previews.md)). The gallery loads an image's original only once the selection rests for 400 ms — each is an `open` gateway call against the per-user rate limit — and its viewer starts a video after the same pause, not one player per keypress. The embed URLs of a page's videos are fetched in one call as the page shows, so stepping from video to video spends none. Inline, a video plays on a click on its poster only; a click in the strip selects.
- **A PDF shows its pages in the gallery and the viewer** (`PdfDocumentView`, pdf.js through `react-pdf`, loaded by `next/dynamic` without SSR): after the same 400 ms rest, loaded whole through the `open` route with `disableRange` — one gateway call, never one per range. Inline it loads by itself only up to `PDF_AUTOLOAD_MAX_BYTES` (`pdf-view.ts`), past that on "Show preview"; the viewer always loads it. Pages are drawn only near the stage. A protected or broken PDF falls back to the placeholder with its reason. `pdfjs-dist` is pinned to the exact version `react-pdf` depends on — bump both together. The files pdf.js fetches at runtime (CMaps, standard fonts, ICC profiles, wasm decoders) are copied from it into the gitignored `public/pdfjs/` by `scripts/copy-pdfjs-assets.mjs`, which `dev` and `build` run first.

  > **Why pdf.js and not the browser's viewer:** [docs/adr/0031-gallery-pdf-rendered-by-pdfjs.md](../../../docs/adr/0031-gallery-pdf-rendered-by-pdfjs.md)
- **The viewer** is one for every view (`useFolderViewer`, owned by `FolderBrowser`): one item over black, stepping through the folder — across its pages — until it is left, a video playing on arrival, a PDF's pages, and anything else a placeholder. From the gallery it is the gallery full screen, on the gallery's selection (`focus`), through all its items. From the grid and the list it keeps an item of its own, off the selection, and steps over the files alone, as Drive's does: the folders, always listed first (`FOLDERS_FIRST` in the service), are a wall (`stepFiles`); a step across pages lands through `pickArrival` (`gallery-navigation.ts`) — Home past a page of folders goes on to the next, a step back onto a page that ends in folders returns; an item deleted under it gives way to its neighbouring file; and on leaving, the item last shown is selected. Its "n / total" counts the files alone too, the listing's `folderTotal` taken out (`getOverallPosition`). It asks for full screen on `document.documentElement`, not on itself — menus, the delete confirmation and notifications open in portals outside it — and closes when the browser leaves full screen (Esc never reaches the page there).
- **A playing video keeps the page's keys.** Keys typed into a cross-origin iframe never reach the page, so the gallery's `BunnyPlayer` runs with `keepPageFocus`: whenever a click gives the player the focus, it goes back to the page (a wrapper around the iframe, inside any dialog's focus trap). The mouse still works the player; its own shortcuts are replaced by the gallery's K / J / L / M, sent through Player.js. A start the browser refuses with sound falls back to a muted one. The player's own full-screen button cannot be hidden from one embed (Bunny's `Controls` are per library), so the gallery takes it over and the button toggles the viewer: the moment an inline player goes full screen, `BunnyPlayer`'s `onFullscreen` hands its playback time to the viewer, which plays on from there (`t`); in the viewer the same button leaves it. **Order matters on the way in:** the document takes the full screen while the player's iframe still holds it (or, refused, after the player has left it), and only then does the viewer replace the inline player — removing the full-screen element leaves full screen altogether. A video's show page keeps the player's own. The viewer closes on leaving full screen only when it went full screen itself, so the player's full screen ending — or a refused request, where the viewer just fills the window — leaves it open.
- **Keys:** ⌘↑ / Backspace go up and Shift+F asks for a new folder in every view (an empty folder included); in the grid and the list the arrows move the selection over the items as laid out (Shift extends it from the anchor; `getArrowTargetId` takes up / down to the nearest row, since the folders and the files are two grids of their own widths), ⌘A selects the page, Esc clears, Enter / ⌘↓ open, F2 renames the one item selected (or the one the keyboard is on), ⌘⌫ / Delete delete the selection; in the gallery ←/→ step — across pages, through `stepGallery` (`gallery-navigation.ts`) — Home/End jump to the ends of the folder, Enter / ⌘↓ open, Space opens the viewer, I the details, F2 renames, ⌘⌫ / Delete delete, ↑ / ↓ and PgUp / PgDn scroll a shown PDF, K plays or pauses a video, J / L seek ∓10 s, M mutes; in the viewer the same, with Enter / ⌘↓ opening the item in a new tab and Space leaving — and nothing else's: the grid's, the list's and the gallery's keys, and going up, rest while it is open. A focused field, an open menu, the delete confirmation (`alertdialog`) or a dialog marked `data-keeps-keys` (the rename and the new-folder dialogs, and the folder picker "Move to…" opens — a key it has no use for is not the gallery's or the viewer's behind it) keeps its keys (`use-window-key-down.ts`) — not every dialog, since the gallery's viewer is one — and the grid's and list's keys rest while a delete, move, rename or new-folder dialog is open. **A letter shortcut is matched through `getShortcutKey`** (`helpers/shortcut-key.ts`), never `event.key` alone: the letter the key types when it is Latin, else the one at its place on QWERTY (`event.code`) — so the keys work on a Cyrillic layout, and stay where they are printed on AZERTY or Dvorak, which `event.code` alone would move. **A key is named on the control it stands for**: at the end of a menu entry (`MenuShortcut` — New's Folder, the "⋮"'s Open, Rename and Delete) or in the control's tooltip. **A key with ⌘ in it is never written by hand**: `useShortcutLabel` (`features/storage/hooks`, over the pure `shortcut-label.ts`) writes a named shortcut as the viewer's keyboard prints it — `⌘⌫` / `⌘A` / `⇧F` on a Mac, `Del` / `Ctrl+A` / `Shift+F` anywhere else — since the handlers take ⌘ and Ctrl alike. The platform is read through `useSyncExternalStore`, with a Mac's labels as the server's answer. The gallery's and the viewer's keys that press nothing on screen — a video's, a PDF's, the ends of the folder — are listed by the keyboard button of their bar (`GalleryShortcuts`), which shows only what the item answers to. Both rules are linted (`shortcutGuard` in `eslint.config.mjs`, `no-restricted-syntax`): a single letter compared with or switched on `.key`, and an Apple key glyph (`⌘ ⌥ ⌃ ⇧ ⌫`) in a string, a template or JSX text anywhere but `shortcut-label.ts` and the specs. Name a key only where it works in every place the control appears: the "⋮"'s Open in new tab has none, since Enter opens the viewer in the grid and the list.

## Forms & fields

- `useValidatedForm(zodShape, props)` (`common/hooks`) wraps Refine's `useForm` with a Zod resolver and also surfaces `providerData` (the loaded record).
- **A backend rule is not checked again in the admin.** A refusal that belongs on a field comes back with a status that singles it out, and the form maps it there. The edit page holds `isPublic` where the folder decides it (`getVisibilityLock`): on in a public folder, which the service would refuse to leave, and the target's value on a move, which the service applies whatever is sent — the checkbox is disabled, says why, and is not sent. The storage-object create and edit pages use `useStorageObjectForm` (`features/storage/hooks`): a 409 is a taken name — only a typed one is ever refused — so it goes on `name` with the backend's message, in place of Refine's notification. A move lands under a suffixed name instead, and the edit page says so. There is no `isExists` lookup before the save. A FILE / IMAGE / VIDEO object places media picked in `MediaSelect` (`features/storage/components`), which lists only what the backend accepts: `placeableMediaFilters` (`features/storage/helpers/media-options.ts`) asks the owner's unplaced READY media, without a file backing an image or a video. The type → resource / create field map is `MEDIA_BY_TYPE` there.
- `TypedController` (`common/components/edit-fields/wrappers`) is a thin generic wrapper over RHF `Controller`; the `Controlled*` inputs (`ControlledTextField`, `ControlledSingleSelect`, `ControlledBooleanField`) and the register-based `*EditField` components build on it. `UserSelect` / `MediaSelect` are async-option selects layered on `ControlledSingleSelect`.
- **A folder is picked the way Drive's "Move to" picks one**, in forms and in the folder browser alike (`features/storage/components/folder-picker`). `FolderPickerDialog` shows one folder at a time, with its path above and its subfolders below: a click picks a subfolder, a double click or its arrow opens it, the path or the back arrow goes up, and with none picked the answer is the folder shown. A search looks through every folder of the owner by name, and a new folder can be made in the one shown (`useCreateFolder`; a taken name is refused inline) — it comes out picked. Every folder that may be entered shows its arrow, an empty one too. Its keys are Finder's, wherever the focus is in the dialog but a field or a button: ↑ / ↓ pick (`stepFolderPick`, over the folders that can be picked), → opens, ← goes up with the folder left picked, Enter confirms, and ↓ leaves the search for the list. It walks the flat list `getFolders` returns, read afresh on every opening (`useUserFolders`), as a tree (`folder-tree.ts`: `toFolderTree`, `getFolderTrail`, `getBlockedFolderIds` for a folder and everything under it, which show but cannot be picked or entered). `FolderPickerField` is the form field over it: the field shows the path and holds the id, and without `required` it can be cleared; its picker opens on the value's parent with the value picked. The edit page hides it for a root folder and blocks the edited folder's own subtree. Every form that places an object — the storage-object create page and the file, image and video create and create-many pages — clears the folder once the owner changes (`useResetParentOnOwnerChange`).
- `GridColumnsBuilder` (`common/utils/grid-columns.builder.tsx`) is a fluent builder for MUI `DataGrid` columns (`.string()/.enum()/.date()/.ref()/.actions()…`), memoized per list page with `useMemo`.
- **List pages** (`common/components/pages/resource-list.page.tsx`) intentionally do **manual** URL sync (`syncWithLocation: false` + `router.push`/`useSearchParams`) behind an `isMounted` gate + `enabled: () => isMounted`. Do **not** migrate this to Refine's built-in `syncWithLocation` / a directly-rendered `DataGrid` — that was tried and reverted because Refine then never fires the initial `getList` (infinite loading) and React throws "state update on a component that hasn't mounted yet". See the note at the top of that file. **The gate also waits for the mount effect's navigation to land** (`useTransition` around its `router.push`): Next's router queue drops a server action sent right after a navigation that interrupted another one — the auth provider's, on a soft navigation — and a `getList` sent from the mount render is that action, so its query loads forever. **The page's own `sortBy` / `sortOrder` stay out of the list's query key** (`meta: URL_SORT_META`): Refine merges every URL parameter it does not know into `meta`, and `meta` into the key, so with them in it every sort was fetched twice — once for `sorters`, once when the URL caught up. The two go together: while the key followed the URL, its change on mount was what loaded the list, in place of the request the queue had dropped.
- **Perf & hooks:** subscribe to specific fields with `watch('field')` / `useWatch` (never the whole-form `watch()`), and read one-off values inside handlers with `getValues()`. Keep hooks at component top level (not inside a `Controller` `render` prop or a conditional) — the shared ESLint preset now enforces `react-hooks/rules-of-hooks` (error) and `react-hooks/exhaustive-deps` (warn).

## Config & commands

`config.service` validates env through `validateEnv`; that call owns each variable's type and default, and the table in [docs/env.md](../../../docs/env.md) is generated from it — change the schema and run `pnpm compile:env-docs` rather than editing the table. All of it is read on the Next server, so nothing there is a `NEXT_PUBLIC_*`. In development the login form comes prefilled from `DEFAULT_EMAIL` / `DEFAULT_PASSWORD`. The `admin` preview in `.claude/launch.json` — the stand a live check runs on, beside `backend` and `storage` — sets them in its own environment, which a `.env` does not override, to a test account of the local dev database that owns sample folders of every type: sign in by submitting the form as it is. The account exists only where it was created; on a fresh database, create it or sign in as the seeded admin.

```bash
pnpm dev              # refine dev (Refine CLI wrapping Next)
pnpm build / start    # refine build / start
pnpm lint             # next lint
pnpm test             # jest over src/**/*.spec.ts — pure helpers only, node environment
```

A spec imports its subject by path, never through a barrel that re-exports React or MUI code, so the suite stays a plain node run with no DOM. `next build` type-checks the specs too, and the tsconfig targets ES5: spread a `Map` iterator through `Array.from`.
