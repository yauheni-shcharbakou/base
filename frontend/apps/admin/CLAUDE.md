# CLAUDE.md — frontend.admin

Guidance for working inside `frontend/apps/admin`. Stack basics (Next 15 App Router, Refine 5, MUI 6, `@frontend/proto`) are in the root `CLAUDE.md`. This file is the app-specific map.

## What it is

The admin panel. Refine resources under `src/app/`: `auth/{users,temp-codes}` and `storage/{files,images,videos,storage-objects}`, each with list / show / edit / create (+ `create-many`) pages, plus auth pages (login, register, forgot-password), and a folder browser at `storage/storage-objects/[id]/content`.

## Data access (the core path)

1. Refine's `grpcDataProvider` (`'use client'`, `features/grpc/providers`) delegates every CRUD call to **Next server actions** (`'use server'`, `features/grpc/actions/grpc.data.actions.ts`).
2. Those actions resolve a repository by resource via `grpcDataService.getRepository(resource)` (`features/grpc/services/grpc.data.service.ts`) and call `getById`/`getList`/`createOne`/… on the **`Grpc*AdminRepository`** variant from `@frontend/proto` — the admin panel talks to the api-gateway `Admin` audience.
3. **gRPC runs on the Next server, not in the browser** — `@grpc/grpc-js` is a Node client. Browser → server action → gRPC → api-gateway (`BACKEND_GRPC_URL`). `authService.getAuthMetadata()` injects the JWT into gRPC metadata on every call.
4. **A server action never throws; it returns an `ActionResult`** (`features/grpc/types`). Wrap its body in `runAction`. The caller unwraps with `unwrapActionResult`, which throws an `Error` carrying `statusCode`, the `HttpError` Refine reads. A 4xx keeps the backend's message. A 5xx or an error without a gRPC status gets a fixed message, and the original is logged on the Next server (`GrpcErrorMapper`, `features/grpc/mappers`; `reportError` does the mapping and the logging). An `app/api` route handler answers a caught error with `errorResponse(error)`, the same mapping as `{ message }` with its status — never `getErrorMessage`, which returns grpc-js `details` verbatim and is for client code. `run-action.ts`, `report-error.ts` and `error-response.ts` load grpc-js, so they are imported by path, and only from server modules. `features/grpc/helpers` has no barrel on purpose.

   > **Why failures travel as values:** [docs/adr/0020-server-action-failures-as-values.md](../../../docs/adr/0020-server-action-failures-as-values.md)

`features/grpc/repositories/index.ts` is the **single source** of `Admin` repository singletons (user, temp-code, file, image, storage-object, video). They are consumed by:

- `features/grpc/services/grpc.data.service.ts` — `GrpcDataService` builds the resource→repository map behind the CRUD data provider from these singletons (no longer instantiates its own).
- the binary-media **route handlers** (`app/api/*`) and the storage create/folder **server actions** (`features/storage/actions/*`), which import the storage repos directly.

The **auth** flow (`features/auth/services/auth.service.ts`) is separate and deliberately uses the `Web`/`Public` audiences (`GrpcUserWebRepository`, `GrpcAuthPublicRepository`): login / refresh / current-user are web-audience calls, not admin CRUD. `getAuthMetadata()` is the single source of gRPC metadata for every authenticated call, upload confirmations included. Login and refresh carry `getClientMetadata()` instead — the browser's address as `x-client-ip`, which the gateway rate-limits them by (see `backend/apps/api-gateway/CLAUDE.md`). **A signed-out session is thrown as a gRPC status, never a plain `Error`** (which `runAction` reports as a 500): a missing or refused refresh token is `UNAUTHENTICATED` (`features/auth/helpers/session-error.ts`, imported by path), a non-admin `PERMISSION_DENIED`. The auth provider reads a 401 / 403 as logged out — `getIdentity` answers `null`, `onError` (reading `statusCode`) logs out. **An expired session is refreshed in `src/middleware.ts`** (Node runtime, for grpc-js), not in the page: a server component cannot write cookies, so a layout's own refresh reached the gateway, threw on the cookie write, and sent a valid refresh token to `/login`. The middleware puts the new cookies on the request (for this render) and the response, and deletes all four when the token is refused; `AuthService`'s own refresh is only the fallback for a server action. **One gateway refresh per refresh token:** a page's parallel requests all arrive without an access token, so `refreshSession` runs them through `SingleFlight` (`features/auth/helpers`) — concurrent callers share one call, and its success is reused for 30 s, for the requests the browser sent with the old cookie before the new one reached it. Only the flights' `Map` lives on `globalThis` (the middleware and the app are separate bundles), never the `SingleFlight` itself: an object that survives a dev reload keeps running the code it was built with. Logout forgets the flight by key **and** by the token it handed out — it is keyed by the old token, and the cookie holds the new one. **This is load-bearing, not an optimisation:** refresh tokens rotate, and auth ends a session whose token is spent twice, so the admin must run as **one process** — a second would refresh the same token on its own and log the user out ([ADR-0029](../../../docs/adr/0029-refresh-token-rotation.md)). **Logout revokes the session** (`AuthService.logout` calls the gateway's public `logout` with the refresh token, then clears the cookies): best effort — a failed call is logged and the cookies go anyway ([ADR-0028](../../../docs/adr/0028-refresh-sessions-in-postgres.md)).

## Binary media (separate path)

Upload, download, open, and player do **not** go through the data provider. Download/open/player use Next **route handlers** under `src/app/api/{files,videos}/[id]/...`, reached by browser navigation alone — `<a download>` (`DownloadButton`), `<a href>`, the preview `<Image>` — so no script reads their error body: a new tab shows the raw JSON, a download or an image just fails. **An embedded player is not one of them:** `BunnyPlayer` (`features/video/components`) loads the signed embed URL itself, fetched by the `getVideoPlayerUrls` server action and cached per video. The requests of one moment — a gallery page's videos, prefetched together — go in one gateway call (`createBatchLoader`, `common/helpers`), and a player keeps the URL it loaded first: a new one would reload the iframe and start the video over. Through the `player` route's redirect the iframe would end on another origin than its `src`, where its `allow` no longer applies — so no autoplay — and Player.js, the Bunny embed's control protocol, would post to the wrong origin. The `player` route is for a new tab only. The two download handlers proxy the signed CDN URL through `features/storage/helpers/download-proxy.ts` (imported by path): **never pass `request.headers` to that `fetch`** — it carries the admin's session cookies to a third party. `toUpstreamHeaders` forwards an allow-list (`Range`, `If-Range`, and `Referer` cut to its origin — the Stream pull zone rejects a request without an allowed referrer) with `Accept-Encoding: identity`, and `toDownloadResponseInit` returns the CDN's status (206 for a range) with `Content-Range` / `Accept-Ranges` / `ETag` / `Last-Modified`, so a browser can resume. **`next/image` runs unoptimized** (`images.unoptimized` in `next.config.mjs`): nothing resizes an image — the storage pull zone has no Optimizer — so an `<Image>` takes its `src` as given, with no `loader`, and the `open` handler redirects to the signed URL untouched ([ADR-0026](../../../docs/adr/0026-folder-listing-carries-signed-previews.md)). See `features/storage` (`use-single/multiple-file-upload`, uploader, per-type action providers) and `features/video`/`image`.

**No upload has a route handler — bytes go from the browser straight to Bunny.** `createOne`/`createMany` return the entity together with credentials, and both upload hooks take a required `uploadFileAction` (`features/storage/types`, the same `Action`-suffix trick as `createManyAction`, for Next's 71007 check) that spends them. Video: `uploadViaTus` (`features/video/helpers`) over Bunny Stream TUS. Files and images: `uploadViaPresignedUrl` (`features/storage/helpers`) PUTs to the pre-signed Bunny Storage URL, then calls the `completeFileUpload` server action — an image completes by its **`fileId`**, not its own id ([ADR-0015](../../../docs/adr/0015-file-uploads-presigned-s3-put.md)). `useMultipleFileUpload` keeps failed items with their created entity, so a retry creates only what has no row yet — or whose `upload.expires` is about to pass. That split and the merge of created entities back into the map are pure functions in `features/storage/helpers/upload-batch.ts`, unit-tested — change the retry rules there, not in the hook. A new selection replaces the old one, and the rows of dropped items (re-selected or removed from the failed list) are deleted through the generic `deleteOne` action, best effort. `VideoActionProvider`/`FileActionProvider`/`ImageActionProvider` flatten the `{ entity, upload }` pair so the hooks still see a flat record; the create pages strip `upload` before handing the record to Refine. **`uploadViaTus` disables tus's fingerprint URL storage on purpose** (`storeFingerprintForResuming: false`, no `findPreviousUploads`): that storage is keyed by the file, not by the `videoId`, so re-uploading the same file resumed the *previous* video's finished upload and left the new row `PENDING` with the UI claiming success. See [ADR-0014](../../../docs/adr/0014-video-uploads-bypass-the-backend.md).

The `file`/`image`/`video` resources are registered in `app/layout.tsx` with `dataProviderName: 'upload'` → a second data provider `grpcUploadDataProvider` (`features/grpc/providers`) whose `create`/`createMany` just echo their variables. Refine's built-in create step is intentionally a no-op for these: the entity row is created and its bytes uploaded by the create pages themselves (create/`create-many`) via the storage server actions + the direct upload helpers.

## Folder browser

`storage/storage-objects/[id]/content` shows one folder of a user's tree: Google Drive's grid and list, and Finder's gallery (`features/storage/components/folder-browser`). It is reached from a user's row (`UserStorageButton` looks up the root folder on click), from a folder's row or show page, and folder to folder from itself.

- **Not a Refine data-provider call.** A folder listing is not a CRUD list, so `useFolderContent` (`features/storage/hooks`) runs its own server action (`getFolderContent`) under `@tanstack/react-query` directly — the same client Refine sets up, pinned to Refine's version so both share one `QueryClient`. The admin `getFolderContent` needs the folder's owner too: a deep link reads the folder first, and every listing remembers the owner of each folder it names, so a step inside a tree is one gateway call.
- **The view's state lives in the URL** — `view`, `sortBy`, `sortOrder`, `page`, `pageSize`, the filters `search` / `types`, and `focus` (the item the keyboard is on: the gallery's selection, or in a grid or list the folder marked on the way up or the item last clicked — never the selection), parsed and patched by the pure `folder-content-params.ts`; a new sort, page size or filter goes back to page 1. A subfolder link keeps the layout and sort and drops the filters: `search` matches this folder's own items only. `setParams` writes through the native history API, which Next syncs with `useSearchParams` — the server renders nothing from these parameters, and a router navigation would fetch the page from it on every arrow key.
- **View and sort are remembered** in the `storage-folder-preferences` cookie (`folder-preferences.ts`), with whether the gallery shows its details. The page is a server component only to read it, so the first render already has them — no flash of the defaults, no listing fetched in the wrong order. The URL wins over the cookie, the cookie over the defaults; a value equal to the viewer's preference stays out of the URL, and only an explicit change (toolbar, list header, info toggle) saves one.
- **A click selects, as in Drive — in the grid and the list.** ⌘/Ctrl-click adds or takes an item, Shift-click selects the range from the anchor, a checkbox (under the pointer, and on every item once one is selected; select-all in the list's header) toggles one, and a drag on the empty space draws a selection box (`useMarqueeSelection`; ⌘/Shift add to what is selected, a click on nothing clears it). Held near the top or the bottom of the screen, the box scrolls the page and grows with it (`getAutoScrollStep`). It works in the container's own coordinates, and it ignores a press that reaches the container through a React portal — an item's open menu or its backdrop — which it would otherwise capture, keeping the menu from closing. The rules are the pure `folder-selection.ts` and `marquee.ts`; `useFolderSelection` holds the selection in memory and only the item the keyboard is on reaches the URL (`focus`). **A selection lasts across the folder's pages, sorts and both Drive views**, so it can be gathered page by page: ⌘A adds the page, the list's header checkbox takes the page back out, and an item on another page is remembered as it was when selected. A new folder or filter starts a new one, and so does the gallery, which keeps its own single selection; leaving the gallery drops its `focus`, so the grid and the list start with nothing selected.
- **A double click or Enter opens**: a folder in place, READY media in a new tab through the `open` / `player` route handlers, and anything not READY on its show page (`getFolderItemTarget`). The kind behind an icon is `getStorageItemKind` — storage type, then MIME type, then extension. Going up — ⌘↑, Backspace, a breadcrumb, Back — marks the folder just left, on the page it was on (`getChildOnPath`, a per-folder last page), as Finder does. Marked is not selected (`focusOnly`): the folder is outlined and has the keyboard — Enter opens it, the arrows start from it — but a checkbox, a ⌘-click or Delete never takes it along unseen.
- **Move and delete act on the selection**, from the bar that lies over the toolbar while something is selected (the toolbar keeps its place, so nothing below jumps), or from an item's "⋮", which acts on the whole selection when the item is part of it and otherwise selects the item alone. Each is one gateway call per 100 items (`deleteStorageObjects` / `moveStorageObjects`, through `runInBatches`), made one after another. A call is all or none; a selection past the gateway's cap of 100 is not, and a run that fails part way reports how many items went through (`StorageBatchError`), which then leave the selection. One call per item would run into the gateway's per-user rate limit. A move goes through "Move to…" (`MoveStorageItemsDialog`, on the folder picker below: it opens on the current folder, which is no target, and the moved folders cannot be entered), or by dragging onto a folder of the page or a breadcrumb above (`useFolderItemBehavior`: native drag and drop under the private `application/x-storage-objects` type, carrying the selection or the dragged item alone). A name taken in the target comes back suffixed, never refused, and the notification lists the renamed items (`getRenamedItems`). A delete asks first (`DeleteStorageItemDialog`, one item or several): the service marks the items — each folder with its whole subtree — deleted, with no restore. `useDeleteStorageObjects` and `useMoveStorageObjects` drop the items from every cached listing at once (`dropFromFolderListings`), then invalidate them; the gallery deletes its one item the same way and selects its neighbour.
- **Files dropped from the desktop upload in place, as in Drive** — onto the folder anywhere, or onto a subfolder or a breadcrumb, which outlines and names the target (`useFileDrop`, and `useFolderItemBehavior` for a folder, which tells a desktop drag — `Files` — from its own private type); "New → File upload" picks them instead. `sortUploads` (`upload-rules.ts`) makes an image or a video its form takes one, keeps anything else a plain file, and leaves out a folder (no tree upload), an empty file and one over its kind's limit, saying which. `UPLOAD_RULES` there are the one copy of those limits and types, which the create forms read as well. The files join `storageUploadQueue` (`use-storage-uploads.ts`): a store outside React, so an upload outlives the page it started on. It creates records with one `createMany` per kind and folder (ten files or images, a video only on its turn, as its credentials are ticking — `pickUploadWork` in `upload-queue.ts`), and runs three transfers at a time. A failed item keeps its record for a retry while the credentials last (`hasUsableCredentials`), and a dismissed one has its record deleted, best effort. `StorageUploadPanel`, mounted once in `app/layout.tsx`, is Drive's box in the corner: progress, retry, and a refresh of the folder listings and media lists as items finish; it asks before the page is left mid-upload. A file dropped beside the folder is swallowed, not opened in the tab. Nothing cancels a transfer yet.
- **Thumbnails come from the listing's `previewUrl` only**, never an original ([ADR-0027](../../../docs/adr/0027-image-preview-made-on-upload.md)); one that fails to load refetches the listing, at most every 30 s, since its signature has likely expired ([ADR-0026](../../../docs/adr/0026-folder-listing-carries-signed-previews.md)). The gallery loads an image's original only once the selection rests for 400 ms — each is an `open` gateway call against the per-user rate limit — and its viewer starts a video after the same pause, not one player per keypress. The embed URLs of a page's videos are fetched in one call as the page shows, so stepping from video to video spends none. Inline, a video plays on a click on its poster only; a click in the strip selects.
- **The viewer** is the gallery full screen: one item over black, stepping through the whole folder until it is left, a video playing on arrival and anything else a placeholder. It asks for full screen on `document.documentElement`, not on itself — menus, the delete confirmation and notifications open in portals outside it — and closes when the browser leaves full screen (Esc never reaches the page there).
- **A playing video keeps the page's keys.** Keys typed into a cross-origin iframe never reach the page, so the gallery's `BunnyPlayer` runs with `keepPageFocus`: whenever a click gives the player the focus, it goes back to the page (a wrapper around the iframe, inside any dialog's focus trap). The mouse still works the player; its own shortcuts are replaced by the gallery's K / J / L / M, sent through Player.js. A start the browser refuses with sound falls back to a muted one. The player's own full-screen button cannot be hidden from one embed (Bunny's `Controls` are per library), so the gallery takes it over and the button toggles the viewer: the moment an inline player goes full screen, `BunnyPlayer`'s `onFullscreen` hands its playback time to the viewer, which plays on from there (`t`); in the viewer the same button leaves it. **Order matters on the way in:** the document takes the full screen while the player's iframe still holds it (or, refused, after the player has left it), and only then does the viewer replace the inline player — removing the full-screen element leaves full screen altogether. A video's show page keeps the player's own. The viewer closes on leaving full screen only when it went full screen itself, so the player's full screen ending — or a refused request, where the viewer just fills the window — leaves it open.
- **Keys:** ⌘↑ / Backspace go up in every view (an empty folder included); in the grid and the list the arrows move the selection over the items as laid out (Shift extends it from the anchor; `getArrowTargetId` takes up / down to the nearest row, since the folders and the files are two grids of their own widths), ⌘A selects the page, Esc clears, Enter / ⌘↓ open, ⌘⌫ / Delete delete the selection; in the gallery ←/→ step — across pages, through `stepGallery` (`gallery-navigation.ts`) — Home/End jump to the ends of the folder, Enter / ⌘↓ open, Space toggles the viewer, I the details, ⌘⌫ / Delete delete, K plays or pauses a video, J / L seek ∓10 s, M mutes. A focused field, an open menu or the delete confirmation (`alertdialog`) keeps its keys (`use-window-key-down.ts`), and the grid's and list's keys rest while a delete or move dialog is open.

## Forms & fields

- `useValidatedForm(zodShape, props)` (`common/hooks`) wraps Refine's `useForm` with a Zod resolver and also surfaces `providerData` (the loaded record).
- **A backend rule is not checked again in the admin.** A refusal that belongs on a field comes back with a status that singles it out, and the form maps it there. The storage-object create and edit pages use `useStorageObjectForm` (`features/storage/hooks`): a 409 is a taken name — only a typed one is ever refused — so it goes on `name` with the backend's message, in place of Refine's notification. A move lands under a suffixed name instead, and the edit page says so. There is no `isExists` lookup before the save. A FILE / IMAGE / VIDEO object places media picked in `MediaSelect` (`features/storage/components`), which lists only what the backend accepts: `placeableMediaFilters` (`features/storage/helpers/media-options.ts`) asks the owner's unplaced READY media, without a file backing an image or a video. The type → resource / create field map is `MEDIA_BY_TYPE` there.
- `TypedController` (`common/components/edit-fields/wrappers`) is a thin generic wrapper over RHF `Controller`; the `Controlled*` inputs (`ControlledTextField`, `ControlledSingleSelect`, `ControlledBooleanField`) and the register-based `*EditField` components build on it. `UserSelect` / `MediaSelect` are async-option selects layered on `ControlledSingleSelect`.
- **A folder is picked the way Drive's "Move to" picks one**, in forms and in the folder browser alike (`features/storage/components/folder-picker`). `FolderPickerDialog` shows one folder at a time, with its path above and its subfolders below: a click picks a subfolder, a double click or its arrow opens it, the path or the back arrow goes up, and with none picked the answer is the folder shown. A search looks through every folder of the owner by name, and a new folder can be made in the one shown (`useCreateFolder`; a taken name is refused inline) — it comes out picked. Every folder that may be entered shows its arrow, an empty one too. Its keys are Finder's, wherever the focus is in the dialog but a field or a button: ↑ / ↓ pick (`stepFolderPick`, over the folders that can be picked), → opens, ← goes up with the folder left picked, Enter confirms, and ↓ leaves the search for the list. It walks the flat list `getFolders` returns, read afresh on every opening (`useUserFolders`), as a tree (`folder-tree.ts`: `toFolderTree`, `getFolderTrail`, `getBlockedFolderIds` for a folder and everything under it, which show but cannot be picked or entered). `FolderPickerField` is the form field over it: the field shows the path and holds the id, and without `required` it can be cleared; its picker opens on the value's parent with the value picked. The edit page hides it for a root folder and blocks the edited folder's own subtree. Every form that places an object — the storage-object create page and the file, image and video create and create-many pages — takes `?userId=&parent=` (`usePresetPlacement`), and clears the folder once the owner changes. The folder browser's "New" menu opens them for the folder shown.
- `GridColumnsBuilder` (`common/utils/grid-columns.builder.tsx`) is a fluent builder for MUI `DataGrid` columns (`.string()/.enum()/.date()/.ref()/.actions()…`), memoized per list page with `useMemo`.
- **List pages** (`common/components/pages/resource-list.page.tsx`) intentionally do **manual** URL sync (`syncWithLocation: false` + `router.push`/`useSearchParams`) behind an `isMounted` gate + `enabled: () => isMounted`. Do **not** migrate this to Refine's built-in `syncWithLocation` / a directly-rendered `DataGrid` — that was tried and reverted because Refine then never fires the initial `getList` (infinite loading) and React throws "state update on a component that hasn't mounted yet". See the note at the top of that file.
- **Perf & hooks:** subscribe to specific fields with `watch('field')` / `useWatch` (never the whole-form `watch()`), and read one-off values inside handlers with `getValues()`. Keep hooks at component top level (not inside a `Controller` `render` prop or a conditional) — the shared ESLint preset now enforces `react-hooks/rules-of-hooks` (error) and `react-hooks/exhaustive-deps` (warn).

## Layout (feature-sliced)

- `src/app/` — App Router: resource pages + auth pages + `api/` route handlers.
- `src/common/` — reusable Refine wrappers (`app-create/edit/show`), layouts, entity/edit fields, hooks (`use-validated-form`, `use-resource-show`), `config.service`, grid-columns builder.
- `src/features/` — `grpc` (data access), `auth` (authProvider + JWT cookie), `storage`, `image`, `video`.

## Config & commands

`config.service` validates env through `validateEnv`; that call owns each variable's type and default, and the table in [docs/env.md](../../../docs/env.md) is generated from it — change the schema and run `pnpm compile:env-docs` rather than editing the table. All of it is read on the Next server, so nothing there is a `NEXT_PUBLIC_*`. In development the login form comes prefilled from `DEFAULT_EMAIL` / `DEFAULT_PASSWORD`. The `admin` preview in `.claude/launch.json` — the stand a live check runs on, beside `backend` and `storage` — sets them in its own environment, which a `.env` does not override, to a test account of the local dev database that owns sample folders of every type: sign in by submitting the form as it is. The account exists only where it was created; on a fresh database, create it or sign in as the seeded admin.

```bash
pnpm dev              # refine dev (Refine CLI wrapping Next)
pnpm build / start    # refine build / start
pnpm lint             # next lint
pnpm test             # jest over src/**/*.spec.ts — pure helpers only, node environment
```

A spec imports its subject by path, never through a barrel that re-exports React or MUI code, so the suite stays a plain node run with no DOM. `next build` type-checks the specs too, and the tsconfig targets ES5: spread a `Map` iterator through `Array.from`.
