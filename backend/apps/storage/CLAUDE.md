# CLAUDE.md — backend.storage

Guidance for working inside `backend/apps/storage`. The 4-layer hexagonal/use-case architecture, `Either` flow, gRPC controllers, and migrations are in the root `CLAUDE.md`; this service follows the same conventions as `backend.auth` (the reference). This file is the service-specific map.

## What this service is

The media / file storage microservice, backed by **Bunny CDN**. gRPC host `storage`, event-bus host `EventBusHost.STORAGE`, database `Database.STORAGE`. More involved than `auth`: 7 modules, an external provider, cross-module deps, event-bus subscriptions, and cron sync.

## Modules (`src/modules/`)

- **storage** — provider abstraction over Bunny (no DB). `StorageFileService` → Bunny **Storage** over its S3-compatible API (`FILE_S3_CLIENT`, an `S3Client` — path-style, checksums only `WHEN_REQUIRED`), `StorageVideoService` → Bunny **Stream** API over axios (`VIDEO_HTTP_CLIENT`). `bunnyStorageConfig` builds the S3 endpoint, API URLs, signed CDN URLs (private key + expiry), and `rootDir` = `dev`/`prod`. **A signed read URL is bound to no client address** — a bearer URL for its lifetime: no URL-map request carries an `ip`, and no pull zone may turn on "Token IP validation" ([ADR-0025](../../../docs/adr/0025-read-urls-bound-to-no-client-address.md)). The storage zone (`BUNNY_STORAGE_ZONE`) and the pull zone serving it (`BUNNY_STORAGE_CDN_ZONE`) are named separately. Exports the two services. Its one controller, `RedisStorageController` (consumer id `storage.storage`), consumes `storage.file.purge` → `StoragePurgeUseCase`, which picks the adapter by `FilePurgeType` (`FILE` → Storage, `VIDEO` → Stream) and never touches the database; a `left` is thrown so BullMQ retries. Both deletes treat "already gone" as success ([ADR-0016](../../../docs/adr/0016-provider-purge-over-the-event-bus.md)).
- **storage-object** — a virtual folder tree (`parent_id`, `name`, `isPublic`, `isFolder`). Event bus (`RedisStorageObjectController`, consumer id `storage.storage-object`): `auth.user.create` → create the user's root folder, `auth.user.delete` → `StorageObjectDeleteRootFolderUseCase` marks the root with its whole subtree under the owner's tree lock (a missing live root is success — the handler is at-least-once); the module emits nothing. Exports `StorageObjectValidationService` and `StorageObjectPlacementService`.
  - **A user's tree is closed.** A parent must be a live folder of the object's own owner (`validatePlacement(parent, userId)`); a foreign, deleted or missing one is the same `NotFound`. A move stays in the moved object's tree, an admin's included; names are checked in the owner's tree only; `userId` never changes. The database holds it too: `storage-objects_parent_owner_foreign` is `(user_id, parent_id) references (user_id, id)` on `storage-objects_owner_id_unique`, declared in the migration as raw SQL (MikroORM cannot key onto a non-primary key — `parent` has `createForeignKeyConstraint: false`), `on delete no action`. CHECKs refuse a self-parent, a `type`/`isFolder` mismatch, an unplaced leaf, and a name that holds `/` or is empty below the root; the gateway's `IsStorageObjectName` turns the last into a 400.
    > **Why in the database and per owner:** [docs/adr/0021-storage-tree-closed-per-owner.md](../../../docs/adr/0021-storage-tree-closed-per-owner.md)
  - **`folderPath` is derived, never stored.** A lazy `@Formula` on `PgStorageObjectEntity` walks up `parent_id` ('/' for a root folder, '/A/B/' for a nested one, null for a leaf), so a move or a rename writes one row and no copy of the path can drift. It is computed only where a read passes `populate: ['folderPath']` — `getById`/`getMany`/`getList` (the gRPC controller's `POPULATE`), `getFolders`, and the folder (not the items) of `getFolderContent` — as a correlated subquery of the same SELECT: a page is one statement (two for `getList`, with its COUNT), never a query per row. Write responses (`createOne`/`updateOne`/`deleteOne`) do not carry it. Call the repository with the populated generic (`getMany<NestStorage.StorageObjectPopulated>(…)`) — without it `E` is inferred as the base entity and `'folderPath'` fails the `keyof` check. Rationale in [ADR-0018](../../../docs/adr/0018-folder-paths-computed-on-read.md).
  - **A folder's `folderStats` is derived the same way.** Another lazy `@Formula` (`type: 'json'`) walks *down* the folder's live subtree and returns `{ fileCount, folderCount, totalSize }`: subfolders at any depth, and the leaves whose file is `READY` with the sum of their sizes (an image or a video counts through its backing file); null for a leaf. `totalSize` is a proto `double` — a sum outgrows `int32`. It is requested by `getById` and `getList` (`POPULATE_WITH_STATS`) and by both the folder and the items of `getFolderContent` — not by `getMany`, `getFolders` or a write's read-back — and it adds no statement. No write keeps it in step, so nothing sorts or filters by it.
    > **Why not stored counters:** [docs/adr/0033-folder-stats-computed-on-read.md](../../../docs/adr/0033-folder-stats-computed-on-read.md)
  - **A folder view is `getFolderContent`, not `getList`.** `StorageObjectGetFolderContentUseCase` reads the folder as a live folder of the given owner (a missing, deleted or foreign id or a leaf is the same `NotFound`) with its `folderPath`, walks up to the root with `getAncestors` (breadcrumbs: root first, its name empty; none for the root), then pages the folder's live objects through `getList` with `file`/`image`/`video` populated and no per-item path. The scope — the folder, its owner, `isDeleted: false` — is set by the use case; the client narrows it only through `StorageObjectFolderContentQuery` (`types`, `isPublic`, `search`, a case-insensitive substring whose `%`/`_` the mapper escapes), never through free-form list filters, which the pg mapper applies over `query` and could widen it with. The order is `isFolder desc` first whatever the client asks, then its `StorageObjectSorter`s (an enum of `NAME`/`CREATED_AT`/`UPDATED_AT`/`TYPE`, `name asc` when none), then `id`: names are unique in a folder, dates and types are not, and an offset page must not repeat or skip a tied row. The items are `StorageObjectFolderItem`s — `StorageObjectPopulated` field for field, which stays untouched as the read model of `getById`/`getList` — and a READY image or video also carries a signed `previewUrl`: the image's preview object (`image.previewProviderId`, made by the `image` module) through `getFileSignedUrl`, or the video's Stream thumbnail through `getThumbnailUrl` — and so does a file with a preview of its own (`file.previewProviderId`, a PDF's first page, made by the `document` module). **An image is never signed by its original** — one without a preview yet, or that cannot have one, carries no `previewUrl`, since the original may be a 100 MB GIF. The signing runs in memory on what the page already populates, so a folder view shows its thumbnails without a URL call per item. `folderTotal` says how many of `total` are folders (a viewer that steps over files alone counts them out): read off the page wherever the folders end on it, since they come first, and a `count` only on a page that cannot tell — files alone past the first page, a full page of folders, a page past the end. Four statements per call, however big the page, five on such a page. `getRootFolder` is the owner's live folder without a parent — `NotFound` before `auth.user.create` is handled and after the user's deletion, never created on a read.
    > **Why the previews ride on the listing, and not on a single item's read:** [docs/adr/0026-folder-listing-carries-signed-previews.md](../../../docs/adr/0026-folder-listing-carries-signed-previews.md)
  - **A folder's `isPublic` reaches its subtree in the same transaction.** `StorageObjectUpdateOneUseCase` writes through `updateAndCascadePublic`, which locks the row, applies the update, and when a folder's `isPublic` changed rewrites every descendant in one recursive `UPDATE`. A move takes the new parent's `isPublic` (`validatePlacement`), so it spreads the same way. A new object — a folder from `createOne` or a leaf from a media create — is public when its folder is, and otherwise takes the caller's `isPublic`, private by default (`resolveIsPublic`): a public folder cannot hold private content, a private one can hold public content. An edit keeps the same rule: making an object private in place while its folder is public is a 400 (`validateVisibility`), unless that folder is made private by the same call.
  - **Tree writes run one at a time per owner.** Every write that checks the tree first runs inside `StorageObjectRepository.withTreeLock(userId, work)`: one transaction holding a transaction-scoped advisory lock keyed by the owner. Repository calls inside the callback join that transaction (media `saveAndPlace*` included), and a `left` rolls it back. Update and delete read the owner once before the lock, then read again inside it; the folder create and every media create (through `StorageObjectPlacementService.placeLeaves`, which also suffixes a batch's names in order) run whole under it. Only database work goes inside — provider calls stay outside. This is what stops two opposite moves from closing a cycle and a create from landing in a folder being deleted, so any new write that checks the tree goes through the same lock. The cleanup crons take none. `getAllChildrenIds` returns `Either`: a failed walk is an error, never an empty set. Rationale in [ADR-0019](../../../docs/adr/0019-tree-writes-under-one-advisory-lock.md) and [ADR-0021](../../../docs/adr/0021-storage-tree-closed-per-owner.md).
  - **A name is unique among a folder's live objects, folders and files alike.** `createOne` refuses a taken folder name and suffixes a taken file name (` (n)`), so an upload never fails on a name; `createFolders` suffixes a taken top-level folder name the same way — nobody typed it. A move — `updateOne` with a new parent, or `moveMany` — lands under a free name through `resolveFreeName`, suffixed on a clash: a folder after its whole name (`v1.2 (1)`), a file before its extension, the object itself excluded. A rename in place refuses a taken name (`validateNameIsFree`): the caller typed it. A deleted object frees its name at once. A taken name is a `ConflictException` (409), the only conflict a create or an edit returns, and it comes only from a typed name — a new folder's or a rename's — so the admin shows it on the name field and keeps no copy of the rule. The partial unique index `storage-objects_name_unique` on `(parent_id, name) where not is_deleted` backs it in the database.
    > **Why a move suffixes and a rename refuses:** [docs/adr/0030-a-move-suffixes-a-taken-name.md](../../../docs/adr/0030-a-move-suffixes-a-taken-name.md)
  - **Names sort through the column's ICU collation, `natural_order` (`und-u-kn`), not the server's libc.** The musl of the alpine image (local, CI) compares bytes and production's glibc does not, so the libc default gave each environment its own order; ICU gives one everywhere — case and accents at the letter they belong to, numbers by value (`file2` before `file10`). It is deterministic, so equality stays byte equality (the unique index refuses the same names) and `ILIKE` works. No property option can declare it: a hand-written migration set it, the snapshot does not know it, and a generated `alter column "name" type …` would silently reset it — add `collate "natural_order"` to one (the e2e order test catches a lost collation). When a Postgres upgrade brings a new ICU, it warns of a collation version mismatch: `reindex index "storage-objects_name_unique"`, then `alter collation "natural_order" refresh version`.
  - **A leaf created through `createOne` places media its owner already holds.** `StorageObjectCreate` carries `file`/`image`/`video` ids (for a future admin picker; media uploads place through `saveAndPlace*` instead). `validateMedia` requires the id matching `type`, none for a folder, and reads it with `getMediaToPlace` scoped to the object's owner: another user's media is `NotFound`, like a missing one. It also refuses media placed already, a file backing an image or a video, and media whose file is not `READY` (an image's and a video's status is its backing file's), all as 400 — not 409, which means a taken name. A picker lists the candidates through the Admin `getList` of `file`/`image`/`video`, filtered on `userId`, `isPlaced: false` and `uploadStatus: READY`, and for files `isBacking: false`: `isPlaced`, `isBacking` and an image's or a video's `uploadStatus` are `computedFilters` of their mappers (`common/infrastructure/pg/factories/pg.media.filters.ts`). An image or a video leaf also references its backing file. The row is built field by field from what was checked, never by spreading the request. The check matters beyond the tree: deleting a leaf lets the file cleanup delete and purge the media under it.
  - **No walk runs forever on a `parent_id` cycle** (moves can no longer close one, but a row written outside the service still can): the id-only CTEs (`markDeletedWithDescendants`, `getAllChildrenIds`, the `isPublic` cascade, the `folderStats` walk) use `UNION`; the walks up — the path formula and `getAncestors` — stop at `MAX_FOLDER_DEPTH`.
  - **The root folder is unique per user and undeletable through the API** — it goes only with its user, on `auth.user.delete`. Uniqueness is a partial unique index (`storage-objects_root_folder_unique` on `user_id where is_folder and parent_id is null`, declared as `@Index({ expression })` on the entity) rather than a read-then-write check — the `auth.user.create` handler is at-least-once, so two replicas (or a stalled BullMQ job) can run it concurrently. `StorageObjectCreateRootFolderUseCase` keeps an `isExists` fast path but treats a `ConflictException` from `saveOne` as success and returns any other error as `left`, which the controller rethrows so the job is retried. `StorageObjectDeleteOneUseCase` rejects a folder with no parent.
  - **Batch moves, deletes and visibility changes are one call, all or none.** `deleteMany` / `moveMany` / `updatePublicMany` (Admin `deleteByIds` / `moveByIds` / `updatePublicByIds`, 1–100 ids at the gateway) name objects of one owner — `validateBatch` reads them live, a missing, deleted or (with `userId`) foreign id is `NotFound`, mixed owners a 400, and an empty list is refused, since an empty `ids` filter matches everything — and run whole under that owner's tree lock. A delete refuses the root among them and marks every subtree in one statement (`markManyDeletedWithDescendants`). A move checks the target once, refuses one inside a moved folder, leaves an object already there as it is, and writes the others in the given order through `updateAndCascadePublic`, each name resolved after the earlier ones landed. It answers each object under the name it ended up with. A visibility change checks the objects' folders once (`validateVisibility`), leaves an object that has the value already as it is, and writes the others through `updateAndCascadePublic`. `createFolders` (Admin too; 1–500 paths of at most 32 levels at the gateway) makes an uploaded directory's tree under one folder in the same way — one call, one lock, all or none: `paths` are relative and "/"-separated, each nested one's parent listed too, saved a level at a time (`saveMany`) so each level has its parents' ids; only the top-level names can clash, and they are suffixed. All four answer `StorageObjectArray`, whose items are `StorageObjectPopulated`, so the controller reads the written rows back with their media (`populate`) before answering: a written row holds its file, image or video as a bare reference, which the gRPC serializer refuses — after the write has gone through.
  - **Delete only marks.** `StorageObjectDeleteOneUseCase` sets `isDeleted` on the object and its whole subtree in one recursive `UPDATE` (`markDeletedWithDescendants`) — non-empty folders included, no restore. The rows go later: the file cleanup cron takes the media under a deleted object (the leaf row follows its file through the FK cascade), and `StorageObjectCleanupUseCase` (`CronStorageObjectScheduler`, every 10 min) deletes deleted folders that have no children left, one level per pass — never a parent first: the parent key is `on delete no action`, so that fails the statement (it once was `set null`, which turned a subfolder into a second root).
- **file** — plain files (Bunny Storage). **This service never receives file or image bytes either**: `createOne`/`createMany` (here and in `image`) return the entity plus a `FilePresignedUpload` (`StorageFileService.getUploadUrl`), the caller PUTs straight to Bunny, then calls `completeUpload` — or `completeMany` for up to 100 files (Admin `completeByIds`), each completed on its own and answered per id with the file or the status it failed with, so one file whose bytes have not arrived does not hold the others back; both run `FileCompletionService.complete` — which HEADs the object (`getObjectSize`) — absent → `Conflict` with the row untouched, wrong size → `FAILED` plus a provider delete, equal → `READY` written only over `PENDING`/`FAILED`, and only the call that wrote it emits `storage.file.ready` (a failed emit is logged; the preview sweeps of `image` and `document` are the backstop). Storage has no webhook, so that call is the only way a row turns READY ([ADR-0015](../../../docs/adr/0015-file-uploads-presigned-s3-put.md)). Plus the `FileCleanupUseCase` cron (every 10 min, at most 500 rows per sweep). **It first turns FAILED every row still PENDING once its upload window has closed** — the longer of the two windows (`uploadWindowMinutes` of `StorageFileService` and `StorageVideoService`, i.e. `BUNNY_STORAGE_UPLOAD_EXPIRES_IN_MINUTES` and `BUNNY_STREAM_TUS_EXPIRES_IN_MINUTES`) plus `UPLOAD_GRACE_MINUTES`, three hours by default: no bytes can arrive any more, so the admin says "failed" and offers to upload again instead of showing an upload "not finished" until the TTL. `failPendingBefore` is one `UPDATE … where upload_status = PENDING`, never the read-then-write `updateMany`, so a confirmation or a provider callback landing meanwhile is not overwritten — and a late one still wins, since `complete` and `uploadFinish` write READY over FAILED. A failed mark is logged and the sweeps go on. It then drops the uploads still PENDING or FAILED past `STORAGE_PENDING_FILE_TTL_HOURS`, and the files placed in a deleted storage object. The cron owns provider cleanup for **every** media type, because `image`/`video` rows are FK-cascaded off the file row: it reads the rows with their `video` relation, deletes them by the ids it just read, then hands each object to `FilePurgeService.purgeFiles` — `VIDEO` by `video.providerId`, `FILE` by the file's own `providerId`, which is set for plain files and images but never for a video — plus the preview — an image's `previewProviderId` when it is an object of its own, else the file's own (a PDF's first page). So every path that deletes file rows reads them with `video` **and `image`** (`FileWithMedia`); the stale-upload sweep reads `video` only, since a file short of READY has no preview. **Every delete path purges through `FilePurgeService` (the `storage.file.purge` event), after the rows are gone** — never inline. **A deleted user's media go with them**: `RedisFileController` also consumes `auth.user.delete` → `FileDeleteByOwnerUseCase` drops every file row of the owner, placed or not, in batches (`getManyByOwner`) and purges each object — the backing file carries the media's owner, so images, videos and their leaves go through the FK cascade. It and the cron share `FileDropService` (delete the ids just read, then purge), and a left is thrown so BullMQ retries. `RedisFileController` also consumes three cross-host `video` events and maps each onto `uploadStatus`: `uploaded` → `UPLOADED`, `uploadFinish` → `READY`, `uploadFail` → `FAILED` — video uploads always create a companion file row. **`UPLOADED` is written only over `PENDING`**, and the query enforces it rather than a read-then-write: the three events sit in three independent queues with independent retry ladders and no ordering between them, so a redelivered `uploaded` can land after `uploadFinish` and would otherwise demote a `READY` row. A miss is the normal outcome there, so the `NotFound` left is swallowed instead of burning ten BullMQ attempts. The cleanup cron sweeps `PENDING`/`FAILED` **only** — `UPLOADED` means an encode is in flight, and a row whose terminal webhook never arrives is rescued by the hourly video sync, not deleted. That sync also lifts to READY a `PENDING` or `FAILED` row whose video Bunny has encoded, so the expired-upload mark above cannot cost a video whose callbacks were lost.
- **user** — the backstop for a lost `auth.user.delete` (an emit that failed after the user row was gone, or a root a retried `auth.user.create` wrote after the delete). `CronUserScheduler` weekly runs `UserPurgeDeletedUseCase`: the owners still holding data (`FileRepository.getOwnerIds` ∪ `StorageObjectRepository.getLiveOwnerIds`) are checked against auth in batches of 500 through `UserDirectoryService` → `GrpcUserDirectoryServiceImpl` (`GrpcUserService.getMany` by `ids`), and every unknown one gets the event's two halves — `StorageObjectDeleteRootFolderUseCase` and `FileDeleteByOwnerUseCase`, both idempotent. An auth reporting zero users (`getList` total) is refused rather than trusted, so a misconfigured `AUTH_GRPC_URL` cannot drop everyone's data; a failed call to auth purges nothing. The only runtime call from storage to auth.
- **image** — images, and **each image's preview**: the object a grid shows, recorded in `images.preview_provider_id`. `RedisImageController` (consumer id `storage.image`) consumes `storage.file.ready` → `ImageMakePreviewUseCase`; `CronImageScheduler` (every 10 min) runs `ImageSweepPreviewsUseCase` over READY images with neither a preview nor `preview_failed_at`, 20 at a time and one after another, READY for over 10 minutes — the backstop for a lost event and the backfill of older images. The use case:
  - makes a **light original its own preview** without reading it — at most 512 px a side and 256 KB, and never a GIF, whose weight is in its frames; an SVG is its own preview up to 256 KB and gets none past it;
  - otherwise hands the original's stream to `ImagePreviewService`, which renders a still webp of at most 512 px a side (`SharpImagePreviewServiceImpl`: the first frame of an animation, EXIF orientation applied, never enlarged, one image at a time), and PUTs it under the derived key `<original without extension>.preview.webp` (`StorageFileService.createPreviewKey`). **The original never becomes a `Buffer`**: the renderer pipes it to a file under `os.tmpdir()`, gives sharp the path and unlinks it in a `finally` — keep it that way, and keep `sharp.cache(false)`, which is what lets libvips let go of the file;
    > **Why a temp file and not a buffer:** [docs/adr/0034-image-original-spooled-to-a-temp-file.md](../../../docs/adr/0034-image-original-spooled-to-a-temp-file.md)
  - answers `left` only for what a retry can fix (the provider, the database, the original's stream breaking mid-read), which the handler throws; undecodable bytes or a missing original set `preview_failed_at` instead, so neither the bus nor the sweep comes back — clear it by hand to retry;
  - records the key only over none (`setPreview`, as `markPreviewFailed`, is `where preview_provider_id is null`), so the handler and the sweep can race; a miss on a deleted image purges the preview it just stored.
  > **Why a preview made on upload, and never the original in a grid:** [docs/adr/0027-image-preview-made-on-upload.md](../../../docs/adr/0027-image-preview-made-on-upload.md)
- **document** — **a PDF's preview**: its first page as a webp of at most 512 px a side, recorded on the file row itself (`files.preview_provider_id`, with `preview_failed_at`) — a PDF has no media row. The same pipeline as `image`, step for step: `RedisDocumentController` (consumer id `storage.document`, its own queue, so image previews never wait behind a PDF; `concurrency: 1`) consumes `storage.file.ready` → `DocumentMakePreviewUseCase`, and `CronDocumentScheduler` (every 10 min) runs `DocumentSweepPreviewsUseCase` over READY files of `PREVIEWABLE_DOCUMENT_TYPES` with neither column set, 20 at a time, READY for over 10 minutes. The use case skips anything but a READY PDF without a preview, marks one over `DOCUMENT_PREVIEW_MAX_BYTES` (50 MB) failed without reading it, reads the rest with `readToBuffer`, and records and fails as `image` does (`setPreview` / `markPreviewFailed` only over none, the preview purged on a miss against a deleted file). **The drawing runs in a worker thread per document** (`PdfjsDocumentPreviewServiceImpl` → `infrastructure/workers/pdf-first-page.worker.ts`: pdf.js loaded by `import()` — it is ESM only — onto `@napi-rs/canvas`): the bytes are transferred, not copied, the worker's heap is capped, and a page that takes over `DOCUMENT_PREVIEW_TIMEOUT_MS` (20 s) or runs it out of memory ends with the worker, marked failed like a protected or broken PDF. The worker file is found by the running file's extension (`.js` in `dist`, `.ts` under ts-node), so the service must stay a per-file build.
  > **Why pdf.js in a worker, and a column on `files`:** [docs/adr/0032-pdf-preview-drawn-by-pdfjs-in-a-worker.md](../../../docs/adr/0032-pdf-preview-drawn-by-pdfjs-in-a-worker.md)
- **Deleting an image or a video deletes its file row too** (`deleteWithFile` on both repositories). The FK cascades `files` → `images`/`videos`, never back, so removing only the media row orphans the file row, and the cleanup cron never reaches a READY one.
- **video** — videos (Bunny Stream); url/download maps and `VideoSyncWithProviderUseCase` (cron) that pages Bunny and `bulkUpdate`s `duration`/`views` by `providerId`. **This service never receives video bytes**: `createOne`/`createMany` return `VideoCreated { video, upload }`, the caller uploads straight to Bunny over pre-signed TUS, and `HttpBunnyStreamWebhookController` turns the provider's status callback into events consumed by `file`. Four callback statuses are actionable: **7** (bytes landed) → `uploaded`; **3** (encoded) → a best-effort `getVideo` that stores `duration`/`views`, then `uploadFinish`; **5**/**8** → `uploadFail` plus a provider delete. The intermediate status exists because Bunny's encode takes up to ~33 minutes, which is otherwise indistinguishable from a dead upload. `VideoSyncWithProviderUseCase` doubles as the backstop: while paging, it makes READY any row short of it — `PENDING`, `UPLOADED` or `FAILED` — whose Bunny object reports finished, since the provider's word is final and a lost callback would otherwise leave an encoded video for the cleanup cron to delete; and it fails a row whose object reports an error, unless the row is `FAILED` already (the object keeps reporting it every pass).

  **Two different Bunny enums are both called `status`** — the webhook's codes (`BunnyStreamStatus`, "Finished" = 3) and a video object's `VideoModelStatus` (`BunnyVideoStatus`, "Finished" = **4**). Each lives next to its consumer; never reuse one for the other.

  **Deleting any media purges the provider regardless of `uploadStatus`** (through `storage.file.purge`). A Stream object exists from `createVideo` — before any byte — and a Storage object from the browser's PUT — before `completeUpload`. A READY gate orphaned every object deleted mid-upload, permanently: the cleanup cron reaches the provider only through the row being deleted. Deleting an absent key is a no-op. Rationale in [ADR-0014](../../../docs/adr/0014-video-uploads-bypass-the-backend.md) and [ADR-0015](../../../docs/adr/0015-file-uploads-presigned-s3-put.md).

## Entities & migrations

- Note: PG entities live in `src/common/infrastructure/pg/entities/` (shared across modules), unlike `auth` where entities sit inside each module.
- **Transactional placement**: `file`/`image`/`video` repositories implement `saveAndPlaceOne`/`saveAndPlaceMany` (not the base `create*`) — inside a single MikroORM `em.transactional`, they persist the entity (`image`/`video` also create their backing `file` row from a `FileMeta`) plus, if a placement `StorageObjectPlacementMeta` is given, a leaf `storage-object` row built by the shared `common/infrastructure/pg/factories/pg.storage-object.factory.ts` (`buildLeafStorageObject` — owns the `type` discriminator, `isFolder: false`, and the file/image/video relation wiring so the three repositories don't duplicate it). **`saveAndPlaceMany` returns the rows in item order**, and the `*CreatedArray` contract rests on it: a create-many answers by position (`items[i]` → `result[i]`), with no correlation key on the wire or in the rows — the use cases zip each saved row with its item's upload credentials the same way.
- `src/mikro-orm.config.ts` lists the four entities; `test/pg.e2e.ts` reads the same list. The migrations are in `src/migrations/`, and nothing in them calls another service — a user's root folder comes from `auth.user.create` alone, the seeded admin's included.

## HTTP surface

Unlike `auth`, this service **listens on HTTP** (`main.ts` calls `app.listen(port)`, with
`rawBody: true`). It serves exactly one route — `POST /webhooks/bunny/stream`, guarded by
`BunnyStreamSignatureGuard`, which verifies the HMAC Bunny computes over the raw body with the
library's *read-only* key. Two things follow: `PORT` must stay clear of `STORAGE_GRPC_URL`'s port,
and in deployment a public domain targets `PORT` alone while the gRPC port stays on the private
network. On Railway that is the only granularity there is — a domain exposes one port of one service
and cannot route by path — so Bunny is given that domain plus the path, and **everything this
listener serves is public**; the signature guard, not the router, is what limits who may call it. `PgRequestInterceptor` only wraps rpc contexts, so an HTTP handler opens its own MikroORM context via `DatabaseRunnerService.isolatedRun` — as the cron schedulers do. Adding a second route widens a perimeter that is otherwise one signed callback.

## Config / env

`config.ts` declares `STORAGE_PENDING_FILE_TTL_HOURS`; everything else lives in the storage module's Bunny config — fourteen `BUNNY_STORAGE_*` / `BUNNY_STREAM_*` variables, nine of them required. Those plus the env of the packages it wires: [docs/env.md](../../../docs/env.md).

## Commands & gotchas

```bash
pnpm start:dev        # nest start --watch
pnpm build / typecheck / migrate (also migrate:create, orm <any CLI command>) / lint
pnpm storage:copy-zone  # one-off copy into a new storage zone — runbook in README.md
pnpm test             # jest: use-cases and services, ports mocked
pnpm test:e2e         # node:test: deletion paths, folder tree, repository errors against Postgres (`pnpm docker:db`), the PDF renderer
```
- **Two runners.** `src/**/*.spec.ts` is Jest. `test/*.e2e-spec.ts` runs on `node:test` under ts-node, because it drives the real repositories and Jest cannot load MikroORM.

  `test/pg.e2e.ts` gives each spec its own `storage_e2e[_<name>]` database (`node --test` runs spec files in parallel processes, and each drops its schema), wipes and migrates it from `src/migrations` on every run, and skips the suite when no server answers. Open the connection in a `before` hook, never in an async `describe` body: `node:test` exits 0 on an error thrown there. A spec that holds a transaction open (the tree-lock specs) must release it in a `finally`: a failed assertion that leaves it open hangs the run on closing the pool instead of failing it.
  > **Why not Jest:** [docs/adr/0017-database-specs-on-node-test.md](../../../docs/adr/0017-database-specs-on-node-test.md)
- `scripts/` sits outside `src/`: `tsconfig.build.json` excludes it (otherwise `nest build` would emit `dist/src/main.js` and break `start:prod`), and `pnpm typecheck` is what type-checks it.
- Event-bus handlers must stay idempotent (at-least-once redelivery, up to 10 BullMQ attempts).
- **`sharp` needs its optional dependencies.** Its native binary is an optional package (`@img/sharp-linuxmusl-x64` in the alpine image), so the Dockerfile's production install must not pass `--no-optional` — without it the first preview fails at `require('sharp')`. `RedisImageController` pins `concurrency: 1` over `REDIS_WORKER_CONCURRENCY`, and the sweep runs sequentially: each render spools an original of up to 100 MB to the temp directory, so that directory must be writable and have the room (`TMPDIR` moves it). **`@napi-rs/canvas`** (the PDF previews) is the same case: its binary is `@napi-rs/canvas-linux-x64-musl` in the image. A PDF render's memory is mostly outside the worker's capped heap — the document, pdf.js's decoders, the canvas — so the service's memory limit must cover about the 50 MB cap plus a few hundred MB (ADR-0032).
- Heavy cross-module wiring (`video` imports `file` + `storage-object` + `storage`; `storage-object` imports `storage` for the previews, never `file`, which imports it) — check for cycles when adding deps.
- `eslint.config.mjs` wires `@packages/configs` `layerGuard()` alongside `nestConfig` — same inward-only import guard as `auth`; keep new imports pointed inward (`interface → infrastructure → application → domain`).
